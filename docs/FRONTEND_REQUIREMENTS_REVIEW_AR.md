# مراجعة متطلبات الفرونت — 2026-10-31

المصدر: LIQAA_BACKEND_REQUIREMENTS_2026-10-31.md الوارد من الفرونت. المقارنة مع الكود المحلي الحالي. هذه مراجعة فقط؛ لم تُنفذ متطلبات إضافية ولم تتغير القاعدة الفعلية.

## نتيجة المراجعة

الوثيقة تضيف تدفقات أعمال فوق فصل الجلسات المنفذ: طلب انضمام وموافقة ودفع للمجموعات، عروض فردية قبل ارتباط الطالب، شراء درس كامل، وأنواع مدرسين واسترداد جزئي ومرفقات استرداد. أسماء الجداول والمسارات فيها مقترحة وليست كلها أسماء موجودة.

| المتطلب | الحالي | العمل المطلوب |
|---|---|---|
| دخول بالهاتف | موجود للطالب والمدرس | الطالب يستخدم /auth/login؛ توحيد alias/DTO إذا اعتمدنا الأسماء الجديدة |
| التسجيل دون بريد | موجود | التسجيل الحالي يطلب region_id وschool_id وgrade وتأكيد كلمة المرور؛ الوثيقة تزيلها وتقترح token فوري، وهذا تغيير مستقل |
| إخفاء بريد الطالب | ليس كاملاً | email ما زال يظهر في userPayload؛ حذفه من DTO الطالب إذا اعتمد المطلوب |
| ربط جهاز الطالب | موجود ومطلوب عند الدخول | الوثيقة لا تذكر device_uuid/platform؛ يجب إبقاؤهما كحقول يرسلها التطبيق تلقائياً أو اعتماد مسار تسجيل وربط واضح |
| تعديل الاسم والصورة فقط | الحالي يسمح أيضاً بالهاتف والبريد والمدرسة والمنطقة والصف | تقييد validation والتحديث؛ رفع الصورة الحالي منفصل باسم avatar |
| online/physical للمدرس | غير موجود بهذا التصنيف | إضافة قدرة المدرس على النمطين أو اشتقاقها بقواعد متفق عليها |
| rating | لا يوجد مصدر تقييم في موديل المدرس | لا نرجع 4.8 تجريبية؛ نحدد مصدرها أو null/غياب الحقل |
| Group/Individual Sessions | منفذ | الحفاظ على sessions.type + type_id وعلى انفصال الحضور والعضوية عن Enrollment |
| المجموعة مرتبطة بمادة/وحدة/درس | الحالي teacher_subject_id فقط | توسيع نطاق المجموعة مع التحقق من ملكية المدرس، دون خلطه بـMorph الجلسة |
| طلب الانضمام وموافقة المدرس | غير موجود | group_join_requests وانتقالات الحالة ومسارات الطالب والأستاذ والإشعارات |
| تفعيل عضوية المجموعة بعد الدفع | غير موجود | سعر/هدف دفع للمجموعة؛ إنشاء group_students.active بعد تثبيت الدفع مع حماية السعة والتكرار |
| انسحاب الطالب | غير موجود كمسار طالب | تحديد المسموح وموعد الانسحاب ومبلغ الاسترداد وفق سياسة أعمال |
| عروض فردية عامة | غير موجود | individual_offers قبل الحجز؛ Individual الحالي مرتبط بطالب محدد وليس عرضاً عاماً |
| الأوقات والحجوزات المدفوعة | موجودة جزئياً | تكييف العقود إلى offer_id/slot_id؛ السعر الحالي على availability وليس عرض نطاق subject/unit/lesson |
| حجز مؤقت 24 ساعة | موجود من إرسال إثبات الدفع | الحفاظ على أصل السياسة؛ يوجد اختلاف بالدفعات المتأخرة يجب حسمه |
| تثبيت دفع بعد مهلة الحجز | الحالي يعيد الفحص وقد يؤكد نفس الموعد إذا ظل متاحاً | الوثيقة تمنع العودة للموعد القديم تلقائياً وتطلب اختياراً جديداً؛ تغيير سياسة واضح |
| بنية المحتوى | موجودة عبر عدة مسارات | يمكن إضافة endpoint تجميعي بدلاً من إنشاء جداول بديلة |
| شراء subject/unit | موجود | subject الحالي هو teacher_subject محدد المدرس، وليس catalog subject وحده |
| شراء lesson | غير موجود كنوع شراء كامل | إضافة سعر للدرس ودعم lesson في Enrollment والدفع وContentAccess؛ content الحالي ليس lesson |
| إنشاء Enrollment | الحالي ينشئ pending قبل الموافقة ثم يفعله | الاتفاق إن كان المقصود بالوثيقة التفعيل فقط أم منع إنشاء سجل pending أصلاً |
| حماية المحتوى | موجودة بصلاحيات وروابط الملفات | إضافة DTO واضح للدرس إن اعتمد؛ flags لا تعني ضمان منع تصوير الشاشة على كل منصة |
| simple/protected quiz | لا يوجد هذا التقسيم | إضافة نوع/سياسة اختبار بسيطة مع إبقاء تحكم الوصول على الخادم |
| دفع شام كاش وسعر الخادم وإثبات | موجود | الحالي checkout_id + provider_reference + proof؛ المطلوب service_type/id + transfer_number + proof_file، يلزم adapter أو عقد واحد |
| منع تكرار دفع المحتوى | موجود | تمديد القاعدة للخدمات الجديدة والمجموعات دون منع حصص مختلفة لنفس العرض |
| استرداد أساسي | موجود مسبقاً | ليس نظاماً يبدأ من الصفر؛ المحافظة على مراجعة الإدارة ومرجع التحويل والتدقيق |
| أهلية الاسترداد | يوجد can_request_refund عام | لا يوجد endpoint حساب مفصل حسب الاستهلاك/الحضور |
| استرداد جزئي | غير مدعوم حالياً | الحالي يطلب كامل payment.amount ويمنع أكثر من طلب فعال/مكتمل؛ يلزم حساب المتبقي ومنع ازدواج الأجزاء |
| إثبات العملية الأصلية وتاريخها في طلب refund | غير موجود بالحقول المطلوبة | تحديد ما يعاد استخدامه من Payment وما يحتاج رفعاً/تاريخاً جديداً |
| إثبات إرسال الاسترداد | الحالي transfer_reference + completed_at | إضافة ملف إثبات وتاريخ تحويل فعلي ومبلغ منفذ والتحقق من صلاحيات الملف |
| أنواع رفض الاسترداد | REJECTED مع review_note | إضافة reason code أو DTO mapping لـrejected_no_balance/rejected_invalid_data |
| إشعارات | يوجد جدول ومسارات وبعض الأحداث | تغطية جميع الأحداث المطلوبة، payload موحد، read endpoint وpagination؛ لا يظهر تكامل FCM في الكود المفحوص |
| تغليف الاستجابة | status/data/meta مع استثناءات | الوثيقة تقترح success/data/pagination؛ اعتماد عقد واجهة/نسخة بدل إعادة تسمية DB |
| رفع الملفات | إثبات الدفع 5120KB والصورة 5120KB حالياً | تعريف حد إثبات الاسترداد الجديد. الأنواع الحالية للدفع PDF/JPG/JPEG/PNG، والصورة تشمل WEBP |

## ما نحافظ عليه من التعديل الأخير

- individuals، group_students، sessions.type/type_id، attendance.student_id.
- progress_notes وprogress_updated_at داخل sessions، دون جدول تقدم مستقل أو content_id/lesson_id لملاحظة التدريس.
- أسماء entities المقترحة مثل physical_groups وgroup_members لا تلزمنا بإنشاء نسخ من groups وgroup_students.
- ContentAsset وVideoAsset وPdfAsset تؤدي دور ملفات وفيديوهات المحتوى؛ لا حاجة لجداول lesson_files/lesson_videos مكررة ما لم توجد متطلبات جديدة محددة.
- طلب انضمام المجموعة شيء مختلف عن GroupStudent؛ لا نضع طالباً كعضو فعال وهو ما زال ينتظر موافقة أو دفعاً.

## قرارات تحتاج تثبيتاً قبل التنفيذ

1. سياسة انسحاب المجموعة: آخر موعد، ما الذي يعد استهلاكاً، هل حضور حصة يمنع الاسترداد الكامل، وهل التسعير لكل حصة أم للحزمة.
2. الاسترداد الجزئي: هل يُسمح بأكثر من دفعة استرداد لنفس الدفع؟ يجب حساب مجموع المكتمل والمحجوز قيد المعالجة ضمن المبلغ المدفوع.
3. التسجيل: هل المدرسة والمنطقة والصف تُنقل إلى onboarding اختياري؟ هل يدخل الطالب فور التسجيل مع ربط جهازه أم يبقى الدخول منفصلاً؟
4. عروض physical: هل شراء العرض يشمل حصة واحدة أو حزمة حصص؟ وكيف تتصل مدة العرض بسعره وبفتحات availability؟
5. بعد انتهاء حجز 24 ساعة: الوثيقة تقترح إعادة اختيار موعد حتى لو القديم متاح؛ الحالي يسمح بتأكيد القديم إذا اجتاز التحقق.
6. ظهور أعضاء المجموعة: هل غير المنضم يشاهد أسماء وصور الطلاب؟ المسار الحالي يتيح قائمة الأعضاء للأعضاء المخوّلين فقط.
7. مدة Enrollment الإلكتروني: هل الوصول دائم أم لمدة محددة حسب المنتج؟ شراء teacher_subject أو unit يغطي المحتوى التابع حالياً ضمن حدود الصلاحية؛ شراء lesson يحتاج التنفيذ الجديد.

## ترتيب تنفيذ مقترح

1. تثبيت عقد المصادقة والبروفايل وأنواع المدرسين وأسماء حالات DTO.
2. إضافة عروض الفردي ونطاق المجموعة وطلبات الانضمام والموافقة.
3. ربط المجموعة/العرض بالدفع وإعادة استعمال بنيته الحالية مع حماية السعة والأوقات.
4. شراء lesson وشاشة محتوى الدرس والاختبار البسيط.
5. أهلية/انسحاب/استرداد جزئي ومرفقات التحويل وفق السياسة المعتمدة.
6. توحيد الإشعارات والتصفح والأخطاء واختبارات التدفقات ثم تسليم عقد نهائي جديد للفرونت.
