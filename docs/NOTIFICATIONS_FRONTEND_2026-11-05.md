# دليل الفرونت: إشعارات الدفع والانضمام والجلسات

تاريخ التجهيز: 2026-11-05. حالة النشر ونتائج تحقق السيرفر في ملف التسليم المرفق، ولا يُعتبر هذا الوصف وحده إثبات نشر.

## 1. جلب الإشعارات

البادئة `/api/v1`، مع `Authorization: Bearer <token>` و`Accept: application/json`.

| الحساب | صندوق الإشعارات الموحّد | الإشعارات الشخصية | تعليم الشخصي كمقروء |
|---|---|---|---|
| الطالب | GET `/student/notification-feed` | GET `/student/notifications` | POST `/student/notifications/{id}/read` |
| الأستاذ | GET `/teacher/notification-feed` | GET `/teacher/notifications` | POST `/teacher/notifications/{id}/read` |

يفضل الصندوق الموحّد. معاملات الصندوق: `kind=all|personal|campaign`, `unread_only=1`, `page=1`, `per_page=20` (الحد 100). استجابة القائمة: `status`, `data[]`, و`meta.current_page, per_page, total, last_page, unread_count`؛ `unread_count` للصندوق الموحّد فقط، وليس للقائمة الشخصية. قد يختلف إجمالي غير المقروء عن عدد نتائج البحث لأن حسابه يسبق فلتر البحث.

```json
{
  "status": true,
  "data": [{
    "id": 123,
    "kind": "personal",
    "key": "personal:123",
    "type": "session_reminder",
    "title": "تذكير بموعد الجلسة",
    "body": "تبدأ جلستك خلال ساعة…",
    "data": {"session_id": 42, "starts_at": "2026-11-05T18:00:00+00:00", "session_type": "group"},
    "read": false,
    "read_at": null,
    "created_at": "2026-11-05T17:00:00.000000Z",
    "related_payment_id": null
  }],
  "meta": {"current_page": 1,"per_page": 20,"total": 1,"last_page": 1,"unread_count": 1}
}
```

المثال توضيحي، وليس بيانات حساب حقيقي. مفتاح إزالة التكرار بالصندوق هو `key`، لأن رقم الحملة قد يساوي رقم إشعار شخصي. للقائمة الشخصية استخدم `personal:<id>`. تحديث حالة القراءة تكراري وآمن. لا ترسل `user_id` لاختيار المستلم. محاولة قراءة إشعار حساب آخر تعيد 404. احفظ التاريخ كوقت مطلق واعرضه بتوقيت المستخدم، دون إضافة ثلاث ساعات يدوياً.

تعليم الحملة كمقروء: POST `/student/notification-campaigns/{id}/read` أو `/teacher/notification-campaigns/{id}/read`. الإشعار الشخصي يبقى على مسار `/notifications/{id}/read`.

## 2. أنواع الأحداث والتنقل

| type | المستلم | متى؟ | الشاشة والمرجع |
|---|---|---|---|
| `payment_submitted` | مدير الشركة النشط | تقديم دفع معلق | رابط مراجعة الدفعة في جرس لوحة الإدارة؛ `related_payment_id` و`data.payment_id` |
| `payment_approved` | الطالب | قبول الدفعة | تفاصيل الدفعة عبر `related_payment_id` |
| `payment_rejected` | الطالب | رفض الدفعة | تفاصيل الدفعة وسبب الرفض في `body` |
| `group_join_requested` | الأستاذ | تقديم طلب جديد | طلبات المجموعة؛ `data.group_id`, `data.join_request_id` |
| `group_join_approved` | الطالب | قبول الطلب | تفاصيل المجموعة؛ `data.group_id` |
| `group_join_rejected` | الطالب | رفض الطلب | تفاصيل الطلب؛ `data.group_id`, وسبب القرار في `body` |
| `session_reminder` | الأستاذ والطلاب المشاركون | خلال الساعة السابقة للجلسة | تفاصيل الجلسة؛ `data.session_id`, `starts_at`, `session_type` |
| `session_cancelled` | الأستاذ والطلاب المشاركون | إلغاء الجلسة | تفاصيل الجلسة وإظهار حالة الإلغاء؛ نفس مراجع الجلسة |

`related_payment_id` هو المرجع الثابت للدفع؛ لا تفترض وجود `data.payment_id` لكل إشعار نتيجة قديم. بعض الحجوزات المدفوعة القديمة تعطي `data.booking_id`. قبول الدفع لا يعني دائماً تثبيت الموعد: إذا احتاج الحجز موعداً بديلاً، الرسالة توضح ذلك؛ اجلب حالة الدفع والحجز من API قبل عرض زر الانضمام. الحجز الحضوري الحالي دفعه عند الأستاذ ولا ينشئ دفعة إلكترونية تلقائياً.

الإلغاء موجود مسبقاً، ومسار الأستاذ POST `/teacher/sessions/{session}/cancel`. إلغاء حجز الطالب DELETE `/sessions/{id}/booking`. استعمل معرّف الجلسة، وليس معرّف المجموعة. عند النقر أعد جلب بيانات الجلسة؛ لا تفتح رابط الجلسة الملغاة من نسخة مخبأة.

طلبات المجموعة: الطالب POST `/student/groups/{group}/join-request`، والأستاذ GET `/teacher/groups/{group}/join-requests` ثم POST `/teacher/groups/{group}/join-requests/{joinRequest}/approve` أو `/reject`. الرفض يحتاج `review_note` غير فارغ. لا يظهر الطالب عضواً قبل القبول.

جرس الإدارة يعرض آخر خمسة إشعارات دفعات لا تزال معلقة، ويخفيها بعد المراجعة. يظهر التغيير عند تحميل الصفحة التالية؛ لم يُضف WebSocket أو تحديث لحظي لصفحة الإدارة المفتوحة.

## 3. Push على الموبايل

POST `/push-tokens`، للحساب المسجّل، بالجسم:

```json
{"fcm_token":"<FCM_TOKEN>","platform":"android"}
```

القيم المقبولة للمنصة `android|ios|web`. حدّث التسجيل عند تغيّر توكن FCM واحذفه عند الخروج عبر DELETE `/push-tokens` مع `fcm_token`. لا ترسل `device_id` أو `user_id`؛ السيرفر يستنتجهما من الجلسة. الطالب يحتاج جهازاً مربوطاً وجلسة جهاز فعالة، والأستاذ يحتاج حساب أستاذ فعالاً. عالج 409 لتعارض ربط التوكن دون إعادة المحاولة بلا نهاية.

FCM يرسل عنواناً ونصاً ومراجع فقط:

```json
{"kind":"personal","notification_id":"123"}
```

لا تتوقع `session_id` أو `payment_id` مباشرة في رسالة Push. عند الاستلام/النقر حدّث الصندوق الموثق، وابحث عن `notification_id` مع تحميل الصفحات اللازمة. إذا لم يعد الإشعار متاحاً افتح صندوق الإشعارات. للحملة يكون `kind=campaign` و`campaign_id`. امنع عرض نسختين من الإشعار نفسه عند اجتماع Push مع تحديث القائمة. تعامل مع فتح التطبيق من حالة الإغلاق ومع المقدمة والخلفية، وبعد الدخول إلى الحساب الصحيح فقط.

قائمة الحساب تظهر الإشعارات حتى لو رفض المستخدم إذن إشعارات النظام. وصول Push يحتاج إعداد Firebase وعامل الصف وتسجيل جهاز صالح؛ الاختبارات البرمجية لا تثبت وصوله إلى هاتف حقيقي.

## 4. اختبارات قبول الفرونت

استخدم حسابات اختبار منفصلة؛ لا تراجع دفعات حقيقية بغرض الاختبار.

| # | الخطوات | المتوقع |
|---|---|---|
| 1 | طالب يقدّم إثبات دفع، والأدمن يعيد فتح لوحة الإدارة | تنبيه باسم الطالب ورابط الدفعة الصحيحة، مرة واحدة |
| 2 | إعادة إرسال نفس الطلب وفق آلية idempotency الحالية | لا دفعة مكررة ولا إشعار تقديم مكرر |
| 3 | الأدمن يقبل الدفعة | `payment_approved` للطالب الصحيح؛ تحديث حالة الدفعة وإخفاء تنبيه المراجعة من اللوحة |
| 4 | رفض دفعة أخرى مع سبب | `payment_rejected` مع السبب الصحيح؛ المحتوى المدفوع لا يُفتح |
| 5 | طالب يطلب الانضمام ثم يكرر الطلب المعلق | إشعار واحد للأستاذ، دون عضوية قبل القبول |
| 6 | الأستاذ يقبل الطلب مرتين | عضوية واحدة وإشعار قبول واحد للطالب |
| 7 | الأستاذ يرفض طلباً آخر مع سبب | إشعار رفض للطالب وحفظ سجل الطلب |
| 8 | جلسة بعد أكثر من ساعة | لا تذكير مبكر |
| 9 | حلول وقت الساعة السابقة وتشغيل المجدول | تذكير للأستاذ وكل أعضاء المجموعة الفعالين أو طالب الفردي |
| 10 | تشغيل المجدول ثانية | لا تكرار؛ حتى إذا حُذف إشعار قديم يبقى سجل منع التكرار |
| 11 | عضو منسحب من المجموعة قبل التذكير | لا تذكير لهذا العضو |
| 12 | إلغاء فردي أو مجموعة من الأستاذ/الإدارة | `session_cancelled` للمشاركين والأستاذ؛ لا تذكير لاحق للجلسة الملغاة |
| 13 | إعادة إلغاء الجلسة | لا إشعار إلغاء مكرر |
| 14 | تغيير الموعد إلى وقت جديد | يمكن إرسال تذكير للموعد الجديد؛ لا يعني ذلك وجود إشعار مستقل لتغيير الموعد |
| 15 | فتح إشعار ثم العودة للقائمة | تحديث القراءة والعداد دون التأثير على حساب آخر |
| 16 | توكن حساب آخر يحاول تعليم الإشعار كمقروء | 404، دون تسريب محتواه |
| 17 | Push في المقدمة والخلفية وبعد إغلاق التطبيق | فتح الشاشة الصحيحة بعد جلب التفاصيل؛ لا نسخة مكررة |
| 18 | رفض إذن إشعارات النظام أو انقطاع الشبكة | الصندوق يبقى قابلاً للاستخدام، مع إعادة تحميل عند عودة الاتصال |

## 5. تحقق الباكند

محلياً نجح 100 اختبار و947 assertion قبل تجهيز النشر، تشمل الدفع والانضمام والجلسات وPush واللوحة. التذكير مسجل كل دقيقة باسم `notifications:session-reminders`؛ التوقيت العملي يعتمد على تشغيل cron، ويعوّض التشغيل المتأخر خلال الساعة فقط. عند النشر يحتاج جدول `session_notification_events` الجديد؛ لا حاجة لحقول جديدة يرسلها الفرونت.
