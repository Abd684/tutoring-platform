# لقاء — الحجز الفردي المباشر بدون عروض

الحالة: منفّذ ومختبر على النسخة المحلية فقط بتاريخ 2026-11-04. لم يُنشر على السيرفر.

هذا العقد يحل محل خطوة IndividualOffer السابقة في التدريس الفردي الفيزيائي. المسار الجديد هو: **اختيار الأستاذ ← اختيار مادة الأستاذ ← اختيار الموعد ← تأكيد الحجز**.

## 1. مصدر السعر والمحتوى

أُضيف إلى `teacher_subjects`:

| الحقل | النوع | المعنى |
|---|---|---|
| `individual_session_price` | decimal(12,2)، nullable | سعر جلسة فردية واحدة |
| `individual_currency` | string من 3 أحرف كبيرة، الافتراضي SYP | عملة سعر الفردي |

السعر مستقل عن `price` الموجود، الذي يبقى سعر شراء المادة إلكترونياً. سعر نافذة التوافر القديمة ليس مصدر السعر في هذا المسار.

- `individual_session_price = null`: الفردي غير مسعّر، فيُمنع الحجز ويظهر `INDIVIDUAL_PRICE_REQUIRED`.
- `individual_session_price = 0`: جلسة مجانية بشكل صريح ومسموحة.
- قيمة موجبة: السعر الذي ينسخه السيرفر إلى الحجز.
- نطاق **حجز الطالب الجديد** هو المادة كاملة: `teaching_scope_type=subject` و`teaching_scope_id=teacher_subject_id`. لا توجد خطوة لاختيار وحدة أو درس في هذا المسار.
- نطاق وأسعار وعملات الحجوزات القديمة لا تتغير. إنشاء الأستاذ اليدوي وعلاقاته القديمة يبقيان على مساراتهما الحالية، بما فيها النطاقات السابقة.

الحجز ينسخ السعر والعملة إلى `individuals.session_price` و`individuals.currency`. تعديل السعر لاحقاً لا يعيد تسعير حجوزات سابقة.

## 2. إعداد السعر من تطبيق الأستاذ

كل المسارات أدناه تبدأ بـ`/api/v1`. العنوان المحلي هو `http://127.0.0.1:8098/api/v1`.

```http
PATCH /api/v1/teacher/subjects/{teacherSubject}
Authorization: Bearer <teacher_access_token>
Accept: application/json
Content-Type: application/json
```

```json
{
  "individual_session_price": 5000,
  "individual_currency": "SYP"
}
```

رد ناجح 200: يحتفظ بعقد مادة الأستاذ القديم ويضيف السعر والعملة:

```json
{
  "status": true,
  "message": "Teacher subject updated successfully.",
  "data": {
    "id": 12,
    "teacher_id": 4,
    "subject_id": 2,
    "price": "250000.00",
    "individual_session_price": "5000.00",
    "individual_currency": "SYP",
    "status": "active",
    "group_enabled": true,
    "max_group_size": 12,
    "subject": {"id": 2, "name": "اللغة العربية", "status": "active"}
  }
}
```

الأرقام والعناوين في أمثلة هذا المستند توضيحية؛ يجب استعمال IDs الراجعة من البيئة الفعلية.

الحقلان مدعومان أيضاً في `POST /teacher/subjects` ضمن الحقول الأصلية لإنشاء مادة الأستاذ. لا تُرسل `teacher_id`؛ الحساب مأخوذ من التوكن.

التحقق:

- السعر nullable، أو رقم بين 0 و9999999999.99.
- العملة 3 أحرف كبيرة، مثال `SYP` أو `USD`. العملة ليست تحويلاً أو صرفاً تلقائياً.
- الأستاذ يملك المادة وحسابه نشط؛ أستاذ آخر لا يستطيع تعديلها.
- لتعطيل الحجز الفردي الجديد للمادة، أرسل `individual_session_price: null`، دون إلغاء الحجوزات السابقة.

## 3. اختيار مادة الأستاذ عند الطالب

استعملوا المسار الموجود:

```http
GET /api/v1/teachers/{teacher}/subjects
Accept: application/json
```

يحافظ على استجابته القديمة ويضيف إلى كل مادة:

```json
{
  "individual_session_price": "5000.00",
  "individual_currency": "SYP"
}
```

رقم العنصر `id` هو `teacher_subject_id` المطلوب للحجز، وليس `subject_id` للمادة العامة. ورقم `{teacher}` هو teachers.id وليس users.id.

إذا السعر null، اعرضوا «الجلسات الفردية غير مسعّرة لهذه المادة» وأوقفوا زر الحجز. لا تستخدموا `price` الإلكتروني بديلاً، ولا تفترضوا أن null يعني مجاناً.

بحث `q` وفلاتر استعراض المواد المحلية يبقيان مدعومين كما في توثيق البحث. فلتر `min_price` و`max_price` في استعراض المواد يقيس سعرها الإلكتروني الحالي، وليس سعر الفردي؛ لا تستخدموه لتصفية أسعار الجلسات.

## 4. جلب المواعيد بدون عرض

```http
GET /api/v1/student/teachers/{teacher}/availability?teacher_subject_id=12&date=2026-11-10
Authorization: Bearer <student_access_token>
Accept: application/json
```

احتفظوا بهيدرات الجهاز المطلوبة حالياً. لم تتغير آلية المصادقة أو ربط الجهاز.

| الحقل | النوع | مطلوب؟ |
|---|---|---|
| `teacher_subject_id` | integer | نعم؛ مادة أستاذ نشطة، ومادتها العامة نشطة، وتخص الأستاذ في المسار |
| `date` | string بصيغة YYYY-MM-DD | نعم؛ اليوم أو تاريخ مستقبلي بحسب تحقق التاريخ الحالي |

`offer_id` ملغى ولا يُرسل. تمريره بقيمة غير فارغة يعيد 422.

مثال رد 200:

```json
{
  "status": true,
  "data": {
    "date": "2026-11-10",
    "teacher_subject_id": 12,
    "session_price": "5000.00",
    "currency": "SYP",
    "teaching_scope_type": "subject",
    "teaching_scope_id": 12,
    "slots": [{
      "availability_id": 34,
      "starts_at": "2026-11-10T10:00:00+03:00",
      "ends_at": "2026-11-10T11:00:00+03:00",
      "timezone": "Asia/Damascus",
      "status": "available"
    }]
  }
}
```

حالات الموعد: `available` متاح، `booked` متعارض مع جلسة أو حجز مالي قديم معلّق صالح، `unavailable` بدأ وقته أو مضى. قد تكون `slots` فارغة. تُراعى تعارضات الأستاذ والطالب معاً، وليست الأستاذ فقط.

لا ترسلوا طلب المواعيد مع كل حرف بحث؛ هذا طلب بعد اختيار مادة وتاريخ. أعيدوا تحميله بعد الحجز أو تغيير التاريخ/المادة.

## 5. إنشاء الحجز

```http
POST /api/v1/student/individual-bookings
Authorization: Bearer <student_access_token>
Accept: application/json
Content-Type: application/json
```

```json
{
  "teacher_subject_id": 12,
  "availability_id": 34,
  "starts_at": "2026-11-10T10:00:00+03:00",
  "ends_at": "2026-11-10T11:00:00+03:00"
}
```

كل الحقول الأربعة مطلوبة. استعملوا الأوقات الراجعة من قائمة المواعيد كما هي مع المنطقة الزمنية، ولا تحذفوا timezone offset.

لا ترسلوا:

- `offer_id`
- `student_id` أو `teacher_id`
- `session_price` أو `currency`
- `teaching_scope_type` أو `teaching_scope_id`

هذه الحقول يُحددها السيرفر، وتمريرها بقيم غير فارغة يعيد 422. الأستاذ يُستخرج من مادة الأستاذ، والطالب من التوكن.

مثال رد 201، بأرقام توضيحية:

```json
{
  "status": true,
  "message": "تم حجز الموعد.",
  "data": {
    "session": {
      "teacher_id": 4,
      "availability_id": 34,
      "type_id": 52,
      "type": "individual",
      "capacity": 1,
      "starts_at": "2026-11-10T07:00:00.000000Z",
      "ends_at": "2026-11-10T08:00:00.000000Z",
      "status": "scheduled",
      "id": 80
    },
    "individual": {
      "student_id": 27,
      "teacher_subject_id": 12,
      "teaching_scope_type": "subject",
      "teaching_scope_id": 12,
      "session_price": "5000.00",
      "currency": "SYP",
      "status": "active",
      "updated_at": "2026-11-04T14:00:00.000000Z",
      "created_at": "2026-11-04T14:00:00.000000Z",
      "id": 52
    },
    "payment_method": "cash_to_teacher",
    "payment_required_on_platform": false
  }
}
```

سعر التأكيد النهائي هو `data.individual.session_price` وعملته `data.individual.currency`. استجابة المواعيد ليست حجزاً للسعر أو للمقعد؛ إذا تغير السعر قبل تنفيذ POST فالسعر الحالي وقت التنفيذ هو المعتمد. يُفضّل إظهار السعر النهائي بعد النجاح، وتحديث بيانات المادة قبل التأكيد عند الحاجة.

الحالة `scheduled` مباشرةً، ولا يوجد قبول عرض أو دفع إلكتروني لهذه الجلسة. لا تنشئوا طلب دفع شام كاش لها.

## 6. قواعد الرفض والواجهة

| HTTP | السبب/التصرف |
|---|---|
| 401 | توكن أو جلسة تسجيل دخول غير صالحة |
| 403 | الحساب/الجهاز غير مسموح له بحسب الحماية الحالية |
| 404 | المادة غير متاحة، أو الموعد لا يخص أستاذها، أو المادة لا تخص الأستاذ في رابط المواعيد |
| 409 مع `INDIVIDUAL_PRICE_REQUIRED` | الأستاذ لم يحدد سعر الفردي؛ اعرضوا رسالة السعر غير المحدد |
| 422 | وقت غير صالح/ماضٍ، حجز جزء من النافذة، توافر معطل، حقول ناقصة أو ممنوعة، أو تعارض الأستاذ/الطالب |

رسالة السعر غير المحدد:

```json
{
  "status": false,
  "code": "INDIVIDUAL_PRICE_REQUIRED",
  "message": "لم يحدد الأستاذ سعر الجلسة الفردية لهذه المادة."
}
```

التعارض يبقى 422 وفق سلوك `IndividualBooking` الحالي؛ لا تعتمدوا أن كل تعارض سيرجع 409. مثال:

```json
{
  "message": "Teacher or student already has an overlapping session.",
  "errors": {"starts_at": ["Teacher or student already has an overlapping session."]}
}
```

الحجز يجب أن يطابق **نافذة الموعد كاملة**؛ تجزئة النافذة ليست ضمن هذا التعديل. على الخطأ، أعيدوا تحميل المواعيد. لا تعيدوا POST تلقائياً بشكل أعمى بعد timeout: افحصوا حجوزات الطالب، فقد يكون الطلب الأول نجح. لا يوجد مفتاح idempotency جديد في هذا التعديل.

العملية داخل معاملة تشمل إنشاء العلاقة الفردية والجلسة والإشعار، مع أقفال الأستاذ والطالب والتوافر ومنع التداخل. فشل الحجز لا يترك علاقة فردية أو إشعاراً جديداً منفصلاً.

## 7. المسارات الملغاة

أُزيلت من تسجيل المسارات المحلي:

- `GET /student/teachers/{teacher}/physical/individual-offers`
- `GET /teacher/individual-offers`
- `POST /teacher/individual-offers`
- `PATCH /teacher/individual-offers/{individualOffer}`

ستعيد 404 محلياً. احذفوا واجهة إدارة العروض عند الأستاذ وخطوة اختيار العرض عند الطالب، ولا تعودوا إليها كخيار احتياطي. لا يوجد نشر لهذا التغيير على السيرفر ضمن هذه المهمة؛ يجب تنسيق نشر الباك وتحديث Flutter معاً لأن العقد القديم تغيّر بطلبكم.

## 8. الترحيل وحفظ التاريخ

الترحيل الجديد:

`2026_11_04_000001_book_individual_sessions_without_offers.php`

- يضيف مصدر السعر والعملة على مادة الأستاذ.
- ينقل سعراً واحداً واضحاً من العروض النشطة للمادة كاملة إن وُجد. إذا اختلفت الأسعار/العملات أو كانت عروض وحدة/درس فقط، يترك السعر null للمراجعة.
- يعيد تسمية `individuals.individual_offer_id` إلى `legacy_individual_offer_id` مع إزالة المفتاح الأجنبي، ويحفظ نسخة JSON من العرض في `legacy_offer_snapshot`.
- يحافظ على جدول العروض كأرشيف للرجوع والتدقيق؛ لا يُستخدم للحجز، ولا يوجد له API إدارة، ونموذجه يمنع الكتابة عبر عمليات Eloquent العادية.
- لا يعيد حساب أسعار الفردي السابقة أو نطاقها أو عملتها، ولا يغيّر الجلسات والمدفوعات والاشتراكات السابقة.
- حقول الأرشيف مخفية من JSON العادي لـIndividual، وعلاقة `individualOffer` أُزيلت.

تم اختبار التطبيق والرجوع وإعادة التطبيق على MySQL المحلية، ومقارنة القيم السابقة في 64 جدولاً. حُفظت نسخ قاعدة محلية خاصة خارج public؛ لا تُرسل هذه النسخ للفرونت.

عند النشر لاحقاً، يلزم أخذ نسخة قاعدة مضمونة أولاً، ثم تطبيق الترحيل ونسخة الكود المتوافقة. إذا احتاج الرجوع إلى إصدار قديم، يجب إرجاع الكود والمخطط معاً. الترحيل يحتفظ بأرشيف العروض لذلك لا نُسقط جدوله.

## 9. التحقق المحلي

- نجاح حجز بمادة وموعد فقط، من دون وجود أي عرض.
- فصل سعر الفردي عن سعر المادة الإلكترونية وعن سعر التوافر القديم.
- رفض مادة أو موعد لأستاذ آخر، والحسابات والمواد غير المتاحة.
- رفض حقن السعر أو الطالب أو الأستاذ أو النطاق أو رقم العرض.
- منع تعارض الأستاذ والطالب، وإظهار الحجز المالي القديم المعلّق كتعارض.
- عدم ترك سجلات علاقة فردية/جلسة/إشعار عند الفشل، وعدم إنشاء دفعة أو اشتراك إلكتروني.
- بقاء سعر الحجز السابق وعملته بعد تعديل سعر الفردي للمادة.
- حفظ ربط الأرشيف والنطاق والسعر والتاريخ بعد الترحيل وإعادته والرجوع عنه.
- تجربة منطق الحجز على MySQL المحلية نجحت ثم تراجعت عن كل سجلات التجربة.
- الاختبار الشامل: 278 اختباراً، 276 ناجحاً و4,340 تحققاً، واختباران متجاوزان متعلقان بـFFmpeg. لم يُنفذ نشر أو اختبار على سيرفر الإنتاج، ولا ربط Flutter فعلي في هذه الخطوة.
