# الدروس المدفوعة والاسترداد اليدوي — عقد الربط

تاريخ التنفيذ: 2026-10-24. امتداد لـ[عقد شام كاش](sham-cash-api.md). لا واجهات جديدة ضمن هذا التسليم، والإشعارات الجديدة مؤجلة. جميع المسارات أدناه تبدأ بـ `/api/v1` وتتطلب `Accept: application/json` وBearer token. مسارات الطالب تتطلب جلسة جهاز وملف طالب فعالين، ومسارات الإدارة دور company_admin فعالاً.

## الاسترداد: طلب من التطبيق وتحويل يدوي من الإدارة

المسار المعتمد: الطالب يطلب → الإدارة تراجع وتوافق أو ترفض → عند الموافقة تنفذ الإدارة التحويل **خارج المنصة يدوياً** → تدخل رقم التحويل الحقيقي لتوثيق الإتمام. لا يرسل Backend المال ولا يستدعي بوابة تحويل شام كاش. الموافقة وحدها لا تعني إتمام التحويل.

المرحلة الحالية تدعم استرداد كامل المبلغ فقط، مرة واحدة للدفع، مع حفظ المحاولات المرفوضة. المبلغ والعملة من سجل الدفع المعتمد، ولا يقبل السيرفر مبلغاً أو حالة استرداد يحددها الطالب. حالة الدفع الأصلية تبقى APPROVED/succeeded وتبقى بياناتها وpaid_at محفوظة بعد الاسترداد.

| Method | Path | الصلاحية | الوظيفة |
|---|---|---|---|
| POST | `/refunds` | صاحب الدفع | إنشاء طلب استرداد |
| GET | `/refunds/my` | طالب | طلباته فقط، مع جميع المحاولات |
| GET | `/refunds/{refund}` | صاحب الطلب/إدارة | تفاصيل طلب |
| GET | `/admin/refunds` | إدارة | قائمة وتصفية الطلبات |
| POST | `/admin/refunds/{refund}/review` | إدارة | الموافقة أو الرفض مع ملاحظة إلزامية |
| POST | `/admin/refunds/{refund}/complete` | إدارة | توثيق التحويل اليدوي الحقيقي بعد الموافقة |

### إرسال الطالب

```json
{
  "payment_id": 81,
  "account_id": "STUDENT-SHAM-ACCOUNT",
  "reason_code": "exceptional",
  "reason": "أطلب استرداد المبلغ للأسباب التالية..."
}
```

payment_id عدد صحيح لدفع شام كاش يملكه الطالب وحالته succeeded. account_id نص غير فارغ حتى 255 حرفاً؛ reason نص غير فارغ حتى 2000 حرف. reason_code أحد:

- `hold_expired`: تأكد الدفع بعد انتهاء المهلة وتعذر تثبيت الموعد الأصلي.
- `teacher_cancelled`: ألغى الأستاذ الدرس.
- `service_unavailable`: تعذرت الخدمة؛ تتحقق الإدارة من السبب يدوياً.
- `exceptional`: استثناء يحتاج قراراً إدارياً موثقاً.

هذه الأسباب لا تمنح موافقة تلقائية. عند مراجعة hold_expired أو teacher_cancelled يتحقق Backend أيضاً من الحالة الفعلية للحجز. يظل التحقق من تعذر تقديم الخدمة والاستثناء مسؤولية الإدارة، ويجب تسجيل مبرر القرار في review_note.

استجابة 201 (مثال توضيحي؛ تظهر الحقول الزمنية وفق تاريخ البيئة):

```json
{
  "status": true,
  "message": "Refund request submitted for manual review.",
  "data": {
    "id": 9, "payment_id": 81, "user_id": 12,
    "amount": "50.00", "currency": "SYP",
    "account_id": "STUDENT-SHAM-ACCOUNT",
    "reason_code": "exceptional", "reason": "أطلب استرداد المبلغ...",
    "status": "PENDING_REVIEW"
  }
}
```

تتضمن الاستجابة الفعلية أيضاً created_at وupdated_at. لا يوجد endpoint للطالب لتغيير الحساب أو المبلغ أو إتمام الطلب بعد إرساله؛ تُراجع الإدارة الحساب المسجل قبل التحويل.

### قرار الإدارة

```json
{"decision":"approve","review_note":"تم التحقق من أهلية الاسترداد ومطابقة الحساب"}
```

أو:

```json
{"decision":"reject","review_note":"سبب رفض طلب الاسترداد"}
```

review_note إلزامية في القرارين، نص غير فارغ حتى 2000 حرف. الحالة تصبح APPROVED أو REJECTED، مع reviewed_by وreviewed_at. الطلب المرفوض يبقى محفوظاً ويمكن تقديم طلب جديد لنفس الدفع. لا يسمح بتغيير قرار الطلب نفسه.

إذا كان الاسترداد يخص درساً، الموافقة تلغي جلسته غير المنتهية وتحرر موعده وتمنع إعادة جدولته. يبقى الاسترداد APPROVED حتى تنفيذ التحويل اليدوي وتوثيقه، ولا يظهر كـCOMPLETED بمجرد الموافقة.

### إتمام التحويل اليدوي

بعد تحويل المبلغ فعلياً إلى account_id المسجل:

```json
{"transfer_reference":"ACTUAL-OUTGOING-SHAM-TRANSFER"}
```

رقم التحويل نص غير فارغ حتى 255 حرفاً؛ يجب أن يختلف عن رقم الدفع الأصلي وألا يكون مسجلاً لاسترداد آخر. لا يقبل الإتمام قبل APPROVED. استجابة 200 تعيد الطلب مع status=COMPLETED وtransfer_reference وcompleted_by وcompleted_at.

عند الإتمام يُلغى الاشتراك المسترد وتُلغى جلساته الفردية غير المنتهية وتزال عضوياته الجماعية، دون إلغاء جلسة المجموعة لبقية الطلاب. إذا كان درساً مدفوعاً تصبح حالة حجزه REFUNDED. هذه تغييرات استحقاق الخدمة؛ سجل الدفع الأصلي لا يُعدّل ولا يُحذف. لا يمكن تقديم استرداد كامل ثانٍ بعد الإتمام.

### الحالات والأخطاء

الحالات المستقلة: `PENDING_REVIEW → APPROVED → COMPLETED`، أو `PENDING_REVIEW → REJECTED`. لا تنفذ أي حالة تحويل مال آلياً.

- 409 REFUND_NOT_ALLOWED: الدفع غير معتمد أو ليس شام كاش.
- 409 REFUND_ALREADY_EXISTS: يوجد استرداد معلق أو موافق عليه أو مكتمل لنفس الدفع.
- 409: محاولة إعادة القرار/الإتمام، الإتمام قبل الموافقة، أو reason_code لا يطابق حالة الحجز عند الموافقة.
- 422: حقول ناقصة/غير صالحة أو رقم تحويل استرداد مستخدم أو يطابق رقم الدفع الأصلي؛ التعارض المتزامن على رقم الاسترداد يرجع 409 REFUND_TRANSFER_ALREADY_USED.
- 404: دفع/طلب غير موجود أو طلب يخص طالباً آخر؛ 403 للأعمال الإدارية من حساب غير مخول.

القوائم تقبل `status=PENDING_REVIEW|APPROVED|REJECTED|COMPLETED` وpage وper_page (20 افتراضياً، من 1 إلى 100)، وتعيد `status,data,meta`. قائمة الإدارة تضيف اسم صاحب الطلب. القرارات والإتمام محفوظة في audit_logs مع المسؤول والتوقيت والملاحظة.

## الدروس المدفوعة وحجز 24 ساعة

شراء درس مدفوع منفصل عن شراء المادة: لا يفتح محتوى المادة ولا يسمح بحجوزات إضافية على إيصال الدرس. للدرس Enrollment من نوع `paid_booking` مخصص لجلسة واحدة، ولا يستخدمه Flutter في مسارات الحجز العادية.

### تسعير الموعد من السيرفر

APIs الأستاذ الحالية لإنشاء/تعديل availability تقبل حقل `price` اختياري بالليرة السورية. null يعني أن هذا الموعد غير معروض للبيع كدرس منفصل. السعر الموجب يخص **نافذة availability كاملة**، لا الساعة ولا جزءاً يختاره الطالب. للمدد/الأسعار المختلفة ينشئ الأستاذ نوافذ منفصلة. الحدود: 0.01 إلى 9999999999.99.

| Method | Path | الوظيفة |
|---|---|---|
| GET | `/teachers/{teacher}/paid-slots` | النوافذ الكاملة المسعرة والمتاحة دون اشتراط شراء مادة |
| POST | `/payments/checkout` | المسار الحالي؛ يقبل service_type=lesson_booking |
| POST | `/student/payments` | multipart الحالي؛ ينشئ الحجز المؤقت مع الدفع |
| POST | `/admin/payments/{payment}/review` | قرار الدفع الحالي؛ يثبت الموعد إذا كان متاحاً |
| GET | `/student/paid-bookings` | سجل الحجوزات المدفوعة للطالب |
| GET | `/student/paid-bookings/{booking}` | تفاصيل الحجز والدفع |
| POST | `/student/paid-bookings/{booking}/reschedule` | تثبيت بديل متاح بعد تعذر الموعد |

paid-slots يقبل from وto اختياريين، مع نهاية بعد البداية وبفترة لا تتجاوز 31 يوماً (7 أيام افتراضياً)، وpage/per_page. from لا يسبق الوقت الحالي. عناصر data تتضمن availability_id وteacher_id وamount وcurrency وstarts_at وends_at بتوقيت UTC. لا تظهر بيانات الطالب الذي يشغل موعداً آخر.

### checkout والإرسال

```json
{
  "service_type":"lesson_booking",
  "service_id":14,
  "starts_at":"2026-10-28T10:00:00Z",
  "ends_at":"2026-10-28T11:00:00Z"
}
```

service_id هنا هو availability_id من paid-slots، وليس subject_id أو session_id. الوقتان إلزاميان ويطابقان النافذة الكاملة. checkout لا ينشئ حجزاً ولا يحتكر الموعد؛ إذا سبق طالب آخر بالإرسال يرجع SLOT_UNAVAILABLE عند محاولة التقديم.

استجابة checkout 201 تتبع عقد شام كاش: checkout_id وinternal_reference وamount وcurrency وaccount_id وqr_url وexpires_at، مع service.type=lesson_booking وبيانات الأستاذ والوقتين. يُرسل checkout_id وprovider_reference وproof عبر multipart `/student/payments` كما في عقد دفع المواد.

من لحظة **نجاح إرسال الإثبات** يُنشأ PaidBooking بحالة HELD وhold_expires_at بعد 24 ساعة، مع دفع PENDING_REVIEW. تمنع أقفال الأستاذ والطالب تعارض الموعد مع الحجوزات المدفوعة أو العادية، ويطبق فهرس رقم التحويل الفريد منع الاستخدام المتكرر. لا يوجد Session نهائي قبل الموافقة.

تغيير السعر قبل الإرسال يرجع PRICE_CHANGED ويتطلب checkout جديداً. التغيير بعد الإرسال لا يعدّل السعر التاريخي. إعادة إرسال نفس checkout ورقم التحويل تعيد نفس الدفع دون حجز أو ملف ثانٍ.

### قرار الدفع وانتهاء المهلة

- تأكيد الدفع والموعد متاح ومستقبلي: APPROVED للدفع، CONFIRMED للحجز، وإنشاء Session مجدول مرتبط بالاشتراك الخاص بالدرس. يظهر في `/student/bookings` و`/student/paid-bookings`.
- رفض الدفع مع السبب: REJECTED للدفع والحجز؛ يحرر الموعد وتبقى المحاولة محفوظة، ويمكن بدء محاولة جديدة.
- انتهاء 24 ساعة: EXPIRED للحجز فقط؛ يبقى الدفع PENDING_REVIEW. لا رفض آلي ولا تفعيل آلي.
- التأكيد بعد المهلة: يفحص Backend الموعد من جديد. إن بقي متاحاً ومستقبلياً يثبته؛ إذا حُجز أو مضى وقته أو تعطلت إتاحته يصبح الدفع APPROVED والحجز NEEDS_RESCHEDULE دون Session نهائي أو فتح المادة.

الأمر `php artisan payments:expire-holds` مسجل كل دقيقة في Laravel scheduler. يجب تشغيل scheduler في السيرفر وفق إعداد النشر؛ الاختبارات لا تعني تشغيل worker دائم. التحقق من صلاحية الحجز يتم أيضاً وقت القراءة والكتابة، فلا يبقى الموعد محجوزاً منطقياً عند توقف scheduler. الأمر يسجل الانتهاء ولا يغير قرار الدفع.

### إعادة الجدولة

بعد اعتماد الدفع ووجود NEEDS_RESCHEDULE، أو إلغاء الأستاذ للدرس، يرسل الطالب:

```json
{
  "availability_id":22,
  "starts_at":"2026-10-29T10:00:00Z",
  "ends_at":"2026-10-29T11:00:00Z"
}
```

البديل نافذة كاملة متاحة للأستاذ نفسه وبنفس المبلغ المدفوع. اختلاف السعر يرجع PRICE_MISMATCH؛ لا يُعدل الدفع التاريخي لتسوية الفرق. يعاد فحص التوفر داخل المعاملة، ويُنشأ Session واحد عند النجاح ويُسجل الموعد السابق في التدقيق. وجود طلب استرداد pending/approved/completed يمنع إعادة الجدولة؛ رفض الاسترداد يعيد إتاحة الخيار.

إعادة الجدولة ليست متاحة للدفع غير المعتمد أو للموعد المثبت بالفعل. إذا لم يناسب البديل الطالب، يقدم طلب استرداد بالطريقة اليدوية أعلاه.

### الإلغاء والتوافق مع المسارات الحالية

إلغاء الأستاذ عبر `/teacher/sessions/{session}/cancel` يحدّث الحجز إلى CANCELLED مع cancelled_by_role=teacher، ويتيح إعادة الجدولة أو طلب الاسترداد. إلغاء الطالب عبر DELETE `/sessions/{session}/booking` لا يمنحه استرداداً تلقائياً، ويمكنه طلب استثناء تراجعه الإدارة. الإلغاء للموعد المستقبلي المجدول فقط. إتمام الدرس يبقى عبر endpoint الأستاذ الحالي.

مسارات الحجز العادية وقراءة التقويم تحتسب الـHELD غير المنتهي كوقت مشغول، ولا تقبل استخدام اشتراك paid_booking لإنشاء درس إضافي. تعديل موعد درس مدفوع من CRUD الأستاذ ممنوع؛ يستخدم مسار إعادة الجدولة. حذف الموعد أو availability المرتبطين بتاريخ مدفوعات ممنوع؛ يستخدم الإلغاء أو تعطيل الإتاحة.

حالات الحجز: `HELD`, `EXPIRED`, `CONFIRMED`, `REJECTED`, `NEEDS_RESCHEDULE`, `CANCELLED`, `REFUNDED`. حالة Session تبقى scheduled/ongoing/completed/cancelled؛ لا تستخدم هذه القيم بديلاً لحالة الدفع أو الاسترداد.

## الحقول الإضافية في استجابة الدفع

تحتفظ APIs الحالية بحقولها وتضيف:

```json
{
  "booking": {"id":5,"status":"NEEDS_RESCHEDULE","session_id":null},
  "refund": {"id":9,"status":"PENDING_REVIEW","amount":"50.00","currency":"SYP","completed_at":null},
  "can_request_refund": false,
  "can_reschedule": false
}
```

booking يعيد تفاصيل سجل الحجز الفعلي بما فيها الأوقات وhold_expires_at؛ المثال يختصرها. booking/refund يكونان null عند عدم وجود سجل. refund يعرض أحدث محاولة. can_request_refund يعني السماح **بتقديم طلب للمراجعة**، وليس ضمان قبول الاسترداد. يظل Backend المرجع النهائي عند تنفيذ الإجراء حتى إذا كانت واجهة التطبيق تعرض حالة سابقة.

## التشغيل والتحقق

أُضيفت وطُبقت محلياً migration `2026_10_24_000002_add_paid_bookings_and_manual_refunds.php` وحدها، مع الحفاظ على بيانات الدفع وQR التجريبيين. يلزم تطبيقها أيضاً على بيئة الربط إن كانت مختلفة وتشغيل scheduler على السيرفر. لا يلزم حساب تحويل حقيقي لتجربة الحالات ببيانات تجريبية؛ لا تمثل استجابة COMPLETED تحويلاً فعلياً دون تنفيذ الإدارة له خارج المنصة.

مجموعة Postman جاهزة للاستيراد: [PaidBookings_Refunds_API.postman_collection.json](../postman/PaidBookings_Refunds_API.postman_collection.json). تبدأ بجلب المواعيد ثم checkout والإرسال، وتشمل طلب الاسترداد ومراجعته وإتمامه؛ انسخ المعرفات من الاستجابات إلى متغيرات المجموعة واختر ملف الإثبات. لا تشغّل approve وreject لنفس الطلب في تسلسل واحد.

نتيجة التحقق المحلي النهائية: **174 اختباراً ناجحاً، 3028 assertion** عبر `php artisan test --compact`، مع نجاح Laravel Pint و`git diff --check` والتحقق من JSON مجموعتي Postman. يؤكد `php artisan schedule:list` تسجيل `payments:expire-holds` كل دقيقة، وشُغّل الأمر محلياً بنجاح دون تغيير أي قرار دفع؛ هذا لا يعني وجود scheduler دائم على سيرفر النشر.

لتشغيل Laravel scheduler على سيرفر Linux، يضبط مسؤول السيرفر مهمة كل دقيقة وفق مسار المشروع الفعلي، مثلاً:

```cron
* * * * * cd /absolute/path/to/tutoring-platform && php artisan schedule:run >> /dev/null 2>&1
```

أثناء التطوير يمكن تشغيل `php artisan schedule:work` في عملية مستمرة. لا تشغّل عمليات مستقلة من التطبيق أو Flutter لتحرير المواعيد.

اختبارات `PaidBookingRefundTest` تغطي checkout/hold، التنافس مع الحجز العادي، انتهاء المهلة مع بقاء الدفع معلقاً، التأكيد المتأخر مع الموعد المتاح/المشغول، عدم فتح المادة بدفع درس، إعادة الجدولة، إلغاء الأستاذ، طلب الاسترداد من الطالب، الصلاحيات والعزل، القرار اليدوي ورقم التحويل، منع التكرار، حفظ المبلغ والتاريخ، وسحب الاستحقاق بعد الاسترداد والتراجع عند فشل التدقيق. اختبار التزامن الفعلي على قاعدة الإنتاج وخط ربط Flutter/لوحة الإدارة يظل اختبار تكامل منفصلاً.
