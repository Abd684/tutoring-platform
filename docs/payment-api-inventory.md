# جرد APIs الدفع وتسليم عقد الربط — لقاء

تاريخ المراجعة: 2026-10-24. المرجع: متطلبات الدفع المرسلة، ومراجعة الكود والمسارات المحلية. هذا جرد للحالة الحالية، وليس إعلاناً باكتمال نظام شام كاش أو تحققاً من بيئة الإنتاج.

> تحديث التنفيذ: هذا الجرد يسجل الوضع **قبل التطوير**. نُفذت بعده المرحلة الأولى لشام كاش؛ راجع [عقد شام كاش الحالي](sham-cash-api.md) للمسارات الجديدة وحدود المرحلة وإيقاف الإرسال القديم بلا إثبات. لا تعتمد وصف النواقص أدناه كحالة لاحقة للتنفيذ.

## قرار التنسيق

يبدأ العمل بتثبيت عقد Backend موثق مع Flutter ولوحة الإدارة. لا يشمل هذا التسليم بناء واجهات أو تغيير تصميم لقاء. يمكن تجهيز حالات العرض على التصميم الحالي ببيانات تجريبية موسومة بوضوح، أما الربط الفعلي فيعتمد فقط على المسارات الموجودة أدناه. المسارات المقترحة لا تصبح جاهزة لمجرد توثيقها.

## 1. APIs الموجودة

البادئة لجميع المسارات أدناه: `/api/v1`. تُرسل `Accept: application/json` و`Authorization: Bearer <token>`. طلبات الطالب تتطلب دور `student` وحساباً وملف طالب فعالين وتوكن جلسة جهاز فعالاً (`student.device`). الإدارة تتطلب `company_admin` فعالاً. هوية الدافع مستخرجة من التوكن.

| الطريقة والمسار | الصلاحية | المدخلات | الحالة الفعلية |
|---|---|---|---|
| POST `/teacher-subjects/{id}/enroll` | طالب | لا حقول مطلوبة | إنشاء اشتراك مادة `pending` بسعر السيرفر؛ 201، والتكرار 409 |
| POST `/units/{id}/enroll` | طالب | لا حقول مطلوبة | شراء وحدة؛ يتطلب سعراً محدداً ونشراً؛ يتحقق من التغطية بالمادة |
| POST `/contents/{id}/enroll` | طالب | لا حقول مطلوبة | شراء محتوى؛ يتحقق من النشر والسعر والتغطية بالمادة أو الوحدة |
| GET `/student/enrollments` | طالب | `page`, `per_page` | قائمة اشتراكات الطالب؛ ليست سجل مدفوعات |
| GET `/student/booking` | طالب | `page`, `per_page` | اشتراكات pending/active غير المنتهية؛ ليست جلسة checkout |
| POST `/student/enrollments/{enrollment}/payments` | صاحب الاشتراك | `provider_reference`: نص إلزامي، حتى 255 حرفاً | إرسال رقم التحويل فقط؛ 201 جديد، 200 يعيد الدفع الموجود pending/succeeded |
| GET `/student/payments/{payment}` | صاحب الدفع | لا شيء | سجل الدفع الخام؛ لا إثبات مرفق ولا بيانات الخدمة الموسعة |
| POST `/admin/payments/{payment}/review` | إدارة | `decision`: `confirm` أو `reject` | يراجع دفعات اشتراك من نوع manual_transfer؛ لا يقبل سبب رفض موثق حالياً |
| GET `/payments` | إدارة | `payer_id`, `status`, `provider`, `provider_reference`, `page`, `per_page` | قائمة عامة مع بيانات الدافع؛ ليست شاشة مراجعة مكتملة البيانات |
| GET `/payments/{payment}` | إدارة | لا شيء | تفاصيل سجل مع بيانات الدافع |
| POST `/payments` | إدارة | حقول CRUD أدناه | موجود تقنياً؛ ليس مسار شراء الطالب ولا يقبل إنشاء دفعات enrollment |
| PUT/PATCH `/payments/{payment}` | إدارة | حقول CRUD | تعديل عام؛ يمنع دفعات enrollment من هذا المسار |
| DELETE `/payments/{payment}` | إدارة | لا شيء | يمنع حذف succeeded فقط؛ يسمح بحذف pending/failed، وهذا يخالف حفظ المحاولات المطلوب |
| GET `/student/notifications` | طالب | لا شيء | آخر 100 إشعار لحساب الطالب؛ إنشاء إشعارات الدفع وPush غير مربوطين بمراجعة الدفع |

`per_page` الافتراضي 20، الحد 100. استجابة القوائم العامة: `status`, `data`, `meta` التي تحتوي `current_page`, `per_page`, `total`, `last_page`.

حقول CRUD الإداري: `payer_id` مستخدم موجود، `payable_type` نص حتى 255، `payable_id` عدد موجب، `amount` من 0.01 إلى 9999999999.99، `currency` ثلاثة أحرف، `provider` حتى 100، `provider_reference` اختياري حتى 255، `status` اختياري من الحالات الحالية، `paid_at` تاريخ اختياري. الحقول الأساسية إلزامية عند الإنشاء، واختيارية عند التعديل. لا يُستخدم CRUD بديلاً عن دورة المراجعة.

## 2. عقد الدفع الحالي وأمثلة الاستجابات

### إرسال رقم التحويل

`POST /api/v1/student/enrollments/42/payments`، بصيغة JSON:

```json
{"provider_reference":"SHAM-TRANSFER-100"}
```

مثال توضيحي لاستجابة 201؛ الأرقام افتراضية، والحقول تعكس الكود:

```json
{
  "status": true,
  "message": "Transfer submitted for administrator verification.",
  "data": {
    "id": 81,
    "payer_id": 12,
    "payable_type": "enrollment",
    "payable_id": 42,
    "amount": "100.00",
    "currency": "SYP",
    "provider": "manual_transfer",
    "provider_reference": "SHAM-TRANSFER-100",
    "status": "pending"
  }
}
```

العملة من `config/payments.php`، افتراضياً SYP ويمكن تغييرها بمتغير `PAYMENT_CURRENCY`. المبلغ مأخوذ من سعر الاشتراك المخزن عند إنشائه، لا من مدخلات الطالب. ليس بالضرورة سعر الخدمة عند إرسال الدفع إذا تغير السعر بين المرحلتين. `id` هو مفتاح قاعدة البيانات بعد الإرسال، وليس رقم محاولة checkout فريداً قبل الإرسال. لا توجد حقول proof أو رقم داخلي مستقل أو تاريخ إنشاء في جدول الدفع الحالي؛ قد يظهر `paid_at: null` عند إعادة جلب السجل.

### المراجعة

```json
{"decision":"confirm"}
```

استجابة 200 تحتوي `status: true` و`message: "Payment review completed."` و`data.payment` و`data.enrollment` (سجلا النموذج الخامان). عند التأكيد تصبح حالة الدفع `succeeded` مع `paid_at`، والاشتراك `active` مع `starts_at` و`expires_at: null`. عند الرفض تصبح حالة الدفع `failed` ويبقى الاشتراك `pending`، ويمكن إرسال دفع جديد على الاشتراك نفسه. إعادة confirm لدفع succeeded تعيد 200 ورسالة `Payment already confirmed.` دون تغيير وقت الدفع؛ هذا سلوك idempotent حالي وليس إجراء مراجعة جديداً.

### الأخطاء

مثال 409 من إرسال الدفع لاشتراك غير pending أو سعره غير موجب:

```json
{"status":false,"message":"Only a pending enrollment with a positive price can be paid."}
```

مثال تحقق 422 افتراضي من Laravel عند غياب رقم التحويل (قد تختلف اللغة بحسب إعداد التطبيق):

```json
{"message":"The provider reference field is required.","errors":{"provider_reference":["The provider reference field is required."]}}
```

| HTTP | الحالة |
|---|---|
| 401 | توكن مفقود/غير صالح أو جلسة جهاز غير فعالة |
| 403 | طالب آخر، دور غير مخول، أو حساب/ملف طالب غير فعال |
| 404 | الاشتراك/الدفع/الخدمة غير موجود |
| 409 | حالة تمنع الإرسال أو المراجعة؛ أو اختلاف مبلغ الدفع/الدافع عن الاشتراك |
| 422 | رقم تحويل مفقود/أطول من 255؛ قرار خارج confirm/reject؛ مراجعة دفع ليس enrollment/manual_transfer |

أخطاء إنشاء الاشتراك تشمل 409 بالأكواد `ALREADY_ENROLLED` و`PRICE_NOT_SET` و`PURCHASE_UNAVAILABLE` و`ALREADY_COVERED_BY_SUBJECT` و`ALREADY_COVERED_BY_UNIT` وفق نوع الخدمة. أخطاء Laravel ليست مغلفة دائماً بـ `status: false`؛ لا يفترض Flutter بنية موحدة قبل توحيد العقد.

## 3. المطلوب مقابل المتوفر

| المتطلب / المسار المقترح في المتطلبات | التقييم | المطلوب من Backend |
|---|---|---|
| GET `/payment-settings` وPUT `/admin/payment-settings` | ناقص | حساب منصة واحد وQR من السيرفر، وصلاحية إدارة التعديل |
| POST `/payments/checkout` | ناقص | جلسة مؤقتة ورقم داخلي فريد، صلاحية زمنية، عدم إظهار دفع للإدارة قبل الإرسال |
| POST `/payments` للطالب | ناقص بهذا العقد | الموجود بهذا الاسم إداري؛ توسيع مسار الطالب أو اعتماد مسار نهائي آخر، لا ربطه بـ CRUD |
| رفع PDF/JPEG/PNG | ناقص | تحقق MIME/حجم، تخزين خاص، عرض/تنزيل مصرح، توثيق multipart |
| GET `/payments/my` | ناقص | سجل جميع المحاولات مع الخدمة والتاريخ وسبب الرفض والاسترداد |
| GET `/payments/{id}` للطالب | مختلف | الموجود للطالب `/student/payments/{payment}`؛ توسيع بياناته أو اعتماد البديل وتوثيقه |
| GET `/admin/payments` | جزئي باسم مختلف | `/payments` إداري موجود؛ ينقصه إثبات/أستاذ/خدمة/تاريخ وبيانات المراجعة |
| approve/reject منفصلان | جزئي بعقد مختلف | `/admin/payments/{payment}/review` موجود؛ سبب رفض إلزامي وسجل مراجع/وقت/قرار ناقصان |
| سعر وبيانات الخدمة وقت التقديم | جزئي | مبلغ/عملة محفوظان؛ السعر من enrollment سابق، ولا snapshot لعنوان الخدمة/الأستاذ |
| منع تكرار الطلب | جزئي | قفل الاشتراك يمنع تكرار الدفع عليه؛ إنشاء الاشتراك نفسه يعتمد فحصاً دون قفل، ويحتاج حماية التزامن لنفس الخدمة |
| منع إعادة استخدام رقم شام كاش | ناقص | الفهرس غير unique ولا يوجد تحقق منع التكرار بين الدفعات |
| حجز مدفوع 24 ساعة | ناقص | APIs حجز موجودة، لكن لا دورة hold مرتبطة بإرسال الدفع ولا تحرير مجدول بعد 24 ساعة |
| إعادة الجدولة بعد انتهاء hold | ناقص | فحص التوفر عند الاعتماد وعرض البديل أو الاسترداد؛ عدم تثبيت موعد غير متاح |
| POST `/refunds`, GET `/refunds/my`, GET `/admin/refunds`, POST `/admin/refunds/{id}/complete` | ناقص | دورة استرداد مستقلة وتحويل يدوي موثق وربط بالدفع الأصلي |
| إشعارات الدفع داخل التطبيق وPush | جزئي | قراءة إشعارات موجودة؛ إضافة أحداث الدفع/الحجز/الاسترداد، إرسال Push وdeep link |
| سلامة الاعتماد والتفعيل | جزئي | transaction وقفل اشتراك ثم دفع موجودان؛ استكمال التدقيق والحجز والإشعارات بعد نجاح المعاملة |
| حفظ السجل المالي والمحاولات | غير مكتمل | منع الحذف والتعديل التاريخي غير المنضبط؛ CRUD يسمح بحذف غير succeeded، وحذف الدافع cascade يحذف مدفوعاته |

لا توجد حالياً آلية multipart للدفع، ولا حد مرفقات مطبق عليه، ولا TTL لجلسة checkout. يجب تسليم قيمها وعقدها قبل الربط، لا افتراضها في Flutter.

## 4. الحالات المعتمدة حالياً وما يحتاج اتفاقاً

| المجال | الحالي | المطلوب في الوثيقة |
|---|---|---|
| الدفع | pending / succeeded / failed / refunded | PENDING_REVIEW / APPROVED / REJECTED؛ الاسترداد مستقل |
| الاشتراك | pending ثم active بعد الاعتماد | فصل تفعيل الخدمة عن قرار الدفع |
| الحجز المؤقت | لا دورة دفع بمهلة 24 ساعة | حالات hold/expiry/confirmation تحتاج عقداً موثقاً |
| الاسترداد | قيمة refunded في الدفع فقط، دون نظام طلبات | حالات مستقلة وأسماء نهائية قبل الربط |

pending↔PENDING_REVIEW وsucceeded↔APPROVED وfailed↔REJECTED مقابلات للتنسيق فقط وليست أسماء بديلة يقبلها API الحالي. لا يغيّر Frontend الحالة بنفسه. يلزم اعتماد أسماء نهائية وخطة توافق/ترحيل إن تغيرت القيم الحالية.

## 5. تسليم Backend والعمل بالتوازي

1. Backend يثبت أسماء المسارات والحقول والحالات في OpenAPI أو مجموعة Postman مع أمثلة نجاح وفشل، الصلاحيات، التصفح والتصفية.
2. يثبت عقد checkout: الرقم الداخلي، وقت الانتهاء، الاستئناف، السعر المعتمد لحظة التقديم، وسلوك الجلسة المنتهية أو المستهلكة والتكرار المتزامن.
3. يثبت عقد multipart: أسماء الحقول الدقيقة وملف الإثبات، الأنواع والحجم الأقصى، أخطاء الرفع وروابط العرض المحمية. لا أسماء حقول مفترضة تصبح نهائية من هذه الوثيقة.
4. ينفذ إعدادات الحساب والإثبات والمراجعة مع سبب الرفض والتدقيق وحماية السجلات؛ ثم يكمل السجل الشخصي والإشعارات.
5. يكمل hold لمدة 24 ساعة وscheduler وإعادة الجدولة والاسترداد، مع حالات مستقلة وروابط واضحة بين الكيانات.
6. Flutter ولوحة الإدارة يجهزان حالات التحميل/المراجعة/الرفض/التفعيل على تصميم لقاء الحالي وفق العقد المثبت، ثم يربطان المراحل المتاحة تباعاً. لا تُعرض الميزات الناقصة كأنها مكتملة.

## 6. خطة القبول من الطلب إلى تفعيل المادة

### المسار الجزئي المتاح الآن

1. دخول طالب بجلسة جهاز فعالة، واختيار مادة نشطة مدفوعة لا يملكها؛ POST enroll يعيد اشتراك pending وسعر السيرفر.
2. التأكد من منع المحتوى المحمي قبل الاعتماد؛ إرسال provider_reference ينتج pending ولا يفعّل الاشتراك، ومحاولة تمرير amount/status لا تتحكم بالقيم المحفوظة.
3. إعادة الإرسال على الاشتراك نفسه تعيد الدفع ذاته؛ طالب آخر لا يستطيع عرضه أو الإرسال عنه، والطالب لا يستطيع مراجعة الدفع.
4. إدارة فعالة ترسل confirm؛ التأكد من succeeded وpaid_at ومن active ووقت بدء الاشتراك ضمن المعاملة.
5. إعادة confirm لا تغير paid_at؛ إعادة قراءة الاشتراك ثم الوصول إلى محتوى منشور مشمول به. هذه الخطوة تحقق الوصول الفعلي، وليس لون زر الشراء فقط.
6. في محاولة منفصلة: reject يجعل الدفع failed ولا يفتح المحتوى؛ إعادة الإرسال تنشئ محاولة جديدة مع بقاء القديمة ما لم تُحذف عبر CRUD الإداري الحالي.

### قبول النظام الكامل بعد التطوير

- الخروج من checkout لا ينشئ دفعاً معلقاً ظاهراً للإدارة، والرقم الداخلي لا يعاد استخدامه؛ انتهاء الجلسة يعيد خطأ موثقاً.
- التلاعب بالسعر أو الهوية أو الخدمة يفشل؛ snapshot يطابق قاعدة السعر المتفق عليها حتى لو تغيّر سعر الخدمة لاحقاً.
- قبول PDF/JPEG/PNG ضمن الحد المعتمد، ورفض MIME مزور/حجم زائد، ومنع الوصول إلى إثبات طالب آخر.
- إرسالان متزامنان لنفس الخدمة لا ينشئان طلبين نشطين، ورقم التحويل المكرر يطبق سياسة المنع/المراجعة الإدارية الموثقة.
- الرفض بلا سبب يفشل؛ الرفض الصحيح يحفظ السبب والمراجع والوقت، ويحفظ المحاولة ويتيح طلباً جديداً.
- الاعتماد المتزامن لا يكرر التفعيل أو الإشعارات؛ فشل التفعيل يرجع المعاملة ولا يترك دفعاً معتمداً بخدمة غير مفعلة دون حالة معالجة صريحة.
- بعد 24 ساعة يتحرر الموعد من السيرفر والدفع يبقى قيد المراجعة؛ التأكيد المتأخر يعيد فحص التوفر ويتيح إعادة الجدولة أو الاسترداد عند التعارض.
- الاسترداد مرتبط بالدفع الأصلي ويتحقق من الأهلية والملكية؛ إتمامه يتطلب رقم التحويل الحقيقي ولا يمحو تاريخ الدفع.
- أحداث التأكيد/الرفض/انتهاء الحجز/البديل أو الاسترداد/اكتمال الاسترداد تصل داخل التطبيق وPush للحساب الصحيح وتفتح تفاصيل الطلب.

## 7. أدلة المراجعة والتحقق

مصادر الكود: `routes/api.php`, `routes/student.php`, `bootstrap/app.php`, `EnrollmentPaymentController`, `PaymentController`, `StudentEnrollmentController`, سياسات Payment/Enrollment، `config/payments.php`، migration إنشاء payments، `routes/console.php` و`ContentAccess`.

تم التحقق من تسجيل مسارات الدفع محلياً باستخدام `php artisan route:list --path=payments` (8 مسارات). اختبارات المراجعة الحالية في `tests/Feature/StudentSessionFlowTest.php` تغطي تثبيت مبلغ السيرفر، منع الطالب من الاعتماد، الاعتماد مرة واحدة، إعادة المحاولة بعد الرفض وعزل الطلاب. هذه ليست اختبارات للنظام الكامل المقترح أو لـPush أو لوصول تحويل شام كاش فعلي.

نتيجة التشغيل المحلي: `php artisan test --compact --filter='StudentSessionFlowTest|StudentCurrentEnrollmentTest|PolymorphicEnrollmentTest'` نجح: 23 اختباراً، 198 assertion، على SQLite in-memory وفق `phpunit.xml`. لا يثبت ذلك منع تعارض الطلبات المتزامنة على قاعدة الإنتاج، ولا يمثل اختباراً آلياً كاملاً من checkout غير الموجود إلى تشغيل المحتوى بعد دفع حقيقي.
